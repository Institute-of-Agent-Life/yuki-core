# Auxiliary model candidate

The host selects a named route from the installed plugin configuration. Each route pins a Profile, allowed purposes, origin kinds and entry scope. The plugin supplies its original call key and bounded input. The host assigns a logical request and records each HTTP attempt through the existing model ledger.

An active tool, command or media handle inherits its original execution and root budget. An observed event can authorize a separately configured event route before participation promotion. That event remains an input dependency. Reading observer metadata alone grants no model route.

The normal sequence resolves the original scope, reserves the logical request atomically, rechecks authority before dispatch, records the physical response and usage, and exposes paged original results. Repeating the same key reads the original request. A changed purpose, route, input or source conflicts. A dispatched request with no response stays unknown across restart.

The acceptance suite will use actual SDK subprocesses and local HTTP peers. It will cover an allowed Jev route, a different Profile, another plugin's handle, revoked scope, one remaining root slot, concurrent same-key calls, process termination before dispatch and after response commit, cancellation during HTTP, and erasure before a late response. Each case checks original logical IDs, attempt counts, root reservations and received HTTP requests.

Result pages belong to the original plugin and current route authority. Source erasure retains request and usage facts while removing request and response content. The public tuple remains a candidate until its real extension consumers supply matching evidence.
