# Auxiliary model candidate

The host selects a named route from the installed plugin configuration. Each route pins a Profile, allowed purposes, origin kinds and entry scope. The plugin supplies its original call key and bounded input. The host assigns a logical request and records each HTTP attempt through the existing model ledger.

An active tool, command or media handle inherits its original execution and root budget. An observed event can authorize a separately configured event route before participation promotion. That event remains an input dependency. Reading observer metadata alone grants no model route.

The normal sequence resolves the original scope, reserves the logical request atomically, rechecks authority before dispatch, records the physical response and usage, and exposes paged original results. Repeating the same key reads the original request. A changed purpose, route, input or source conflicts. A dispatched request with no response stays unknown across restart.

The acceptance suite will use actual SDK subprocesses and local HTTP peers. It will cover an allowed Jev route, a different Profile, another plugin's handle, revoked scope, one remaining root slot, concurrent same-key calls, process termination before dispatch and after response commit, cancellation during HTTP, and erasure before a late response. Each case checks original logical IDs, attempt counts, root reservations and received HTTP requests.

Result pages belong to the original plugin and current route authority. Source erasure retains request and usage facts while removing request and response content. The public tuple remains a candidate until its real extension consumers supply matching evidence.

Private context from additional events declares those IDs in `sources`. Each reference must already belong to the original parent or be retained by this plugin within the approved entry. The request binds these dependencies before reservation. Erasure of an extra context source also fences a late response, while preserving its accounting. Static instructions can omit source references.

An operator can install a Jev route for an existing participation scope. Its
`profile` pins the endpoint, request model, environment key reference and root
budget. The route's `jev` table pins `response_model` and `timeout_seconds`. It
requires event origins in the same enabled participation entries. The original
human event must belong to the current generation. For any additional context,
declare the retained event IDs in `sources` from the same entry and generation.
This can include the canonical SELF delivery already returned as that human
event's `reply_to` by `participation.source`. The Host verifies the retained
reply before dispatch and result reads. Erasing the delivery's original input
removes its derived request and response content while retaining usage.

On that route, send `jev: {state, questions}` with the original call key. The
Host supplies the configured model and sends the native three-field request.
`llm.result` pages the original response's JSON, including the model, answers
and any usage. The participation library validates its rubric and decides
whether the result supports a proposal. The common ledger retains numeric usage
even when the returned model is wrong. An interrupted physical attempt stays
unknown, and a same-key read returns its original receipt. This is an
unpublished candidate for EXT-025.

An installation can enable `[reflection_budget]` in `yuki.toml`. It defaults to
`timezone = "Asia/Shanghai"` and `max_daily_calls = 96` when the table is
present. The shared limit counts committed physical attempts for `reflect`
calls from maintenance origins, including unknown outcomes. The Host checks it
in the dispatch transaction against the recorded attempt time. A full quota
defers the original unpaid call, which remains eligible under the same key
when the next local day opens. Paid result reads and preview application keep
their original authorization and can settle at the limit.
